# Feature Specification: 프로필 이미지 업로드 및 변경

**Feature Branch**: `002-profile-image-upload`

**Created**: 2026-08-06

**Status**: Draft

**Input**: User description: "마이페이지에서 프로필 이미지 업로드 및 변경 기능을 구현해줘. 이 기능은 Supabase와 연동될꺼야. 사진은 스토리지의 profile-image 버킷에 uuidv4 파일명으로 저장되어야해. 그리고, 그 이미지의 다운로드URL은 앞부분(스토리지 주소)와 뒷부분(버킷명 이후)을 나누고, 앞부분은 환경변수에 저장할거고, 뒷부분은 profile테이블의 image_path에 저장되어야해. 환경변수는 .env.example에 작성해주면, 내가 .env.local에 옮겨적을게."

## Clarifications

### Session 2026-08-06

- Q: 업로드된 사진을 `profile-image` 버킷 안 어디에 저장할까요? → A: 사용자별
  폴더 — `<사용자ID>/<uuid>.<확장자>` 구조로 저장하고, 폴더명으로 소유권을
  저장소 정책 수준에서 강제한다.
- Q: 사진을 올리기 전에는 무엇을 보여줄까요(구글 계정 아바타 폴백 여부)? →
  A: 기본 아이콘(셰프 모자) 유지 — 구글 아바타는 사용하지 않으며, 직접
  업로드한 사진만이 프로필 이미지의 유일한 출처다.
- Q: 업로드 전에 이미지를 자동 축소할까요, 원본 그대로 올릴까요? → A: 원본
  그대로 — 5MB 상한 검사만 하고 축소·포맷 변환 없이 선택한 파일을 그대로
  저장한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 프로필 이미지 최초 업로드 (Priority: P1)

로그인한 사용자가 마이페이지 프로필 카드에서 사진을 선택해 업로드하면, 기본
아이콘 대신 자신의 프로필 사진이 표시된다.

**Why this priority**: 기능의 핵심 가치. 이것 하나만 구현해도 "내 사진이 있는
프로필"이라는 사용자 가치가 완성되는 최소 단위다.

**Independent Test**: 이미지가 없는 계정으로 마이페이지에 진입해 사진을
업로드하고, 프로필 카드에 그 사진이 표시되는지 확인하는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 프로필 이미지가 없는 로그인 사용자가 마이페이지에 있을 때,
   **When** 프로필 이미지 영역의 업로드 진입점을 눌러 유효한 이미지 파일을
   선택하면, **Then** 업로드가 진행되고 완료 후 프로필 카드에 해당 사진이
   표시된다.
2. **Given** 업로드가 완료된 상태에서, **When** 저장소를 직접 확인하면,
   **Then** 파일은 `profile-image` 버킷에 원본 파일명이 아닌 UUID v4 기반
   파일명으로 저장되어 있고, 사용자 프로필 레코드의 `image_path`에는 버킷명
   이후의 경로만 저장되어 있다.
3. **Given** 업로드 중일 때, **When** 사용자가 화면을 보고 있으면, **Then**
   진행 중임을 알 수 있는 시각적 피드백(로딩 상태)이 표시된다.

---

### User Story 2 - 프로필 이미지 변경 (Priority: P2)

이미 프로필 사진이 있는 사용자가 새 사진을 선택하면 기존 사진이 새 사진으로
교체되고, 화면에 즉시 반영된다.

**Why this priority**: 최초 업로드 다음으로 중요한 반복 사용 시나리오.
업로드와 동일한 흐름을 재사용하므로 P1 위에 얹는 증분이 작다.

**Independent Test**: 이미지가 이미 있는 계정으로 마이페이지에서 다른 사진을
선택해, 새 사진이 표시되고 프로필 레코드의 경로가 새 파일을 가리키는지 확인.

**Acceptance Scenarios**:

1. **Given** 프로필 이미지가 있는 사용자가 마이페이지에 있을 때, **When** 새
   이미지 파일을 선택해 업로드하면, **Then** 프로필 카드가 새 사진으로 즉시
   갱신되고 `image_path`가 새 파일 경로로 교체된다.
2. **Given** 이미지 교체가 완료된 상태에서, **When** 저장소를 확인하면,
   **Then** 이전 이미지 파일은 저장소에서 제거되어 있다(제거 실패가 사용자
   흐름을 막지는 않는다).

---

### User Story 3 - 저장된 이미지의 지속 표시 (Priority: P3)

사용자가 앱을 새로고침하거나 다시 로그인해도, 저장된 경로를 기반으로 프로필
사진이 계속 표시된다. 이미지가 없거나 불러올 수 없으면 기본 아이콘이 표시된다.

**Why this priority**: 업로드된 이미지가 세션을 넘어 유지됨을 보장하는
마무리 시나리오. P1·P2가 저장을 올바르게 했다면 표시 로직만 추가하면 된다.

**Independent Test**: 이미지를 업로드한 계정으로 새로고침·재로그인 후
마이페이지에서 같은 사진이 표시되는지, 경로가 깨진 계정에서 기본 아이콘으로
대체되는지 확인.

**Acceptance Scenarios**:

1. **Given** 프로필 이미지를 업로드한 사용자가, **When** 새로고침하거나
   재로그인 후 마이페이지에 진입하면, **Then** 동일한 프로필 사진이 표시된다.
2. **Given** `image_path`가 비어 있는 사용자가, **When** 마이페이지에
   진입하면, **Then** 기본 아이콘(현행 셰프 모자)이 표시된다.
3. **Given** `image_path`가 존재하지만 실제 파일을 불러올 수 없을 때,
   **When** 마이페이지에 진입하면, **Then** 깨진 이미지 대신 기본 아이콘이
   표시된다.

---

### Edge Cases

- 이미지가 아닌 파일(문서·동영상 등)을 선택하면? → 업로드를 시작하지 않고
  허용 형식을 안내한다.
- 용량 상한을 초과한 파일을 선택하면? → 업로드를 시작하지 않고 상한을
  안내한다.
- 업로드 도중 네트워크가 끊기면? → 실패를 안내하고 기존 이미지(또는 기본
  아이콘) 상태를 유지한다.
- 파일 업로드는 성공했지만 프로필 레코드 갱신에 실패하면? → 사용자에게는
  실패로 안내하고 기존 상태를 유지한다(고아 파일은 허용하되 흐름을 막지
  않는다).
- 업로드가 진행 중인데 사용자가 다시 업로드를 시도하면? → 진행 중에는 중복
  시도를 막는다(버튼 비활성/로딩 표시).
- 다른 사용자의 프로필 이미지를 업로드·교체하려는 시도는? → 인증된 본인
  프로필에 대해서만 허용된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 마이페이지 프로필 카드에서 사용자는 프로필 이미지를 업로드하고
  변경할 수 있는 진입점을 가져야 한다.
- **FR-002**: 시스템은 이미지 파일 형식(JPEG·PNG·WebP)만 허용하고, 파일당
  최대 5MB의 용량 상한을 적용해야 한다. 위반 시 업로드를 시작하지 않고
  사유를 안내한다.
- **FR-003**: 업로드된 파일은 스토리지의 `profile-image` 버킷 안 해당
  사용자의 폴더에 `<사용자ID>/<uuid>.<확장자>` 경로로 저장되어야 한다.
  파일명은 UUID v4 기반이며 원본 파일명은 사용하지 않는다.
- **FR-004**: 이미지 접근 URL은 두 부분으로 관리되어야 한다 — 앞부분(스토리지
  기본 주소~버킷명까지)은 환경변수로, 뒷부분(버킷명 이후의 파일 경로)은
  사용자 프로필 레코드(`profiles.image_path`)에 저장한다. 화면 표시는 두
  부분을 조합해 이루어진다.
- **FR-005**: 새로 도입되는 환경변수는 키와 용도 설명이 `.env.example`에
  추가되어야 한다(실제 값은 사용자가 `.env.local`에 기입한다).
- **FR-006**: `image_path`가 비어 있거나 이미지를 불러올 수 없으면 기본
  아이콘을 표시해야 한다.
- **FR-007**: 업로드·변경 성공 시 페이지 이동이나 새로고침 없이 프로필
  카드가 즉시 갱신되어야 한다.
- **FR-008**: 업로드 진행 중에는 로딩 상태를 표시하고 중복 업로드 시도를
  막아야 한다.
- **FR-009**: 업로드·레코드 갱신 실패 시 사용자 친화적 에러 메시지를
  표시하고 기존 이미지 상태를 유지해야 한다.
- **FR-010**: 이미지 업로드·변경은 인증된 사용자가 본인 프로필에 대해서만
  수행할 수 있어야 하며, 저장소 수준에서도 본인 폴더(`<사용자ID>/`) 밖에는
  쓰기·삭제가 불가능해야 한다.
- **FR-011**: 이미지 변경 시 이전 이미지 파일은 저장소에서 제거를 시도해야
  한다. 제거 실패는 사용자 흐름(변경 성공)을 막지 않는다.

### Key Entities

- **프로필(profiles)**: 사용자당 1개 존재하는 프로필 레코드. 기존
  `image_path`(선택 값) 필드에 버킷명 이후의 이미지 파일 경로를 보관한다.
  값이 없으면 "이미지 미설정" 상태를 의미한다.
- **프로필 이미지 파일**: `profile-image` 버킷 안 사용자별 폴더에 저장되는
  이미지 오브젝트. 경로는 `<사용자ID>/<uuid>.<확장자>` 형태로, 파일명은
  UUID v4 기반이라 업로드별로 고유하며 원본 파일명을 포함하지 않는다.
  `image_path`에는 이 경로 전체(사용자 폴더 포함)가 저장된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 마이페이지 진입 후 3회 이하의 인터랙션(진입점 클릭 →
  파일 선택 → 확인)으로 프로필 사진 업로드를 완료할 수 있다.
- **SC-002**: 상한(5MB) 이내의 사진은 일반적인 네트워크 환경에서 10초 이내에
  업로드·화면 반영이 완료된다.
- **SC-003**: 업로드·변경 후 새로고침이나 재로그인을 해도 프로필 사진이
  100% 동일하게 표시된다.
- **SC-004**: 형식·용량 위반, 네트워크 실패 등 모든 실패 경로에서 사용자는
  무반응·무한 로딩 없이 명확한 안내를 받는다.

## Assumptions

- 사용자 프로필 테이블(`profiles`)과 `image_path` 컬럼(선택 값)은 이미
  존재하므로 스키마 변경 없이 재사용한다. 사용자가 언급한 "profile 테이블"은
  기존 `profiles` 테이블을 가리키는 것으로 본다.
- `profile-image` 버킷은 아직 없으므로 본 기능 구현 시 생성한다. 프로필
  사진은 민감 정보가 아니므로 공개 읽기(누구나 URL로 조회 가능)를 허용하고,
  쓰기(업로드·삭제)는 인증된 본인만 가능한 것으로 한다 — URL 앞부분을
  환경변수로 고정 관리한다는 요구는 서명 없는 안정적인 공개 URL을 전제로
  한다.
- 허용 형식은 JPEG·PNG·WebP, 용량 상한은 5MB를 기본값으로 한다.
- 업로드 시 이미지 자동 축소·포맷 변환은 하지 않는다. 상한 검사만 통과하면
  선택한 원본 파일이 그대로 저장된다.
- 이미지 크롭·회전·필터 등 편집 기능은 범위 밖이다.
- 구글 계정 프로필 사진(외부 아바타 URL) 연동은 하지 않는다. 업로드 전
  상태는 항상 기본 아이콘이다.
- 이미지 "삭제 후 기본 아이콘으로 되돌리기" 기능은 요청되지 않았으므로 범위
  밖이다(업로드와 변경만 다룬다).
- 마이페이지 프로필 카드(이름 표시·수정)는 이미 구현되어 있으며, 본 기능은
  그 카드의 아이콘 영역을 이미지 표시·업로드 진입점으로 확장한다.

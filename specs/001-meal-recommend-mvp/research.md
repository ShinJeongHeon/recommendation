# Research: 집밥 요리 추천 서비스 MVP

**Date**: 2026-08-04 | **Plan**: [plan.md](./plan.md)

Technical Context의 미지수를 모두 결정으로 치환한다. 각 항목은 Decision / Rationale / Alternatives considered 형식.

## R1. 플랫폼 — 모바일 우선 PWA

- **Decision**: 설치형 PWA(모바일 우선 반응형 웹 앱)로 출시한다. 네이티브 앱은 게이트 통과·수익 검증 이후로 미룬다.
- **Rationale**: 1인 프로젝트 단계에서 앱스토어 심사·배포 파이프라인 비용이 0이다. 스펙의 가정("모바일 우선 앱 형태, 명세는 기술 중립")과 충돌하지 않고, 홈 화면 설치로 "앱을 연다"는 경험을 제공한다. 웹 푸시가 가능해 PRD 오픈 이슈(접점 채널)를 나중에 코드 변경 없이 이어붙일 수 있다. KR1(1분 내 확정)은 네이티브 성능을 요구하지 않는다.
- **Alternatives considered**: ① 네이티브(iOS/Android) — 검증 전 단계에서 스토어 배포·이중 코드베이스 비용 과다, 기각. ② React Native/Expo — 단일 코드베이스이지만 빌드·배포 복잡도가 여전히 웹보다 높고, 게이트 실패 시 매몰 비용이 큼, 기각. ③ 순수 웹(비설치형) — 채택안의 부분집합이며 PWA 매니페스트 추가 비용이 미미해 설치형으로 확장.

## R2. 프레임워크 — React 19 + Vite 7

- **Decision**: UI는 React 19, 개발 서버·번들은 Vite 7. PWA는 vite-plugin-pwa.
- **Rationale**: 리포에 이미 Vitest 4(내부적으로 Vite 기반)가 설정되어 있어 툴체인이 자연스럽게 이어진다. 화면 5개 규모에서 프레임워크 간 성능 차이는 무의미하므로 생태계·자료가 가장 풍부한 기본값을 선택해 1인 개발 속도를 우선한다.
- **Alternatives considered**: ① Svelte — 번들이 작지만 팀 확장·자료 면에서 이점이 상쇄, 기각. ② 바닐라 TS + 직접 DOM — 화면 상태(추천 고정, 지침 모드, 확인 질문 흐름)가 수동 관리로 번잡해짐, 기각. ③ Next.js — 서버 기능이 필요 없는데 프레임워크 무게만 추가, 기각.

## R3. 백엔드 — 없음 (정적 호스팅 단독)

- **Decision**: MVP는 서버·DB·계정 없이 클라이언트 단독으로 동작한다. 배포는 정적 호스팅.
- **Rationale**: 스펙 가정(단일 사용자 로컬 프로필, 로그인 범위 외)과 정합. 카탈로그 30개·제철·시세·보관기간은 모두 저빈도(월 단위) 갱신 정적 데이터라 빌드 시점에 번들하면 된다. 서버 제거로 운영 비용 0, 개인 식사 데이터가 기기 밖으로 나가지 않아 프라이버시 리스크도 제거된다.
- **Alternatives considered**: ① BaaS(Firebase 등) — 다기기 동기화는 MVP 요구가 아님, 도입 시 인증·보안 규칙 관리 비용 발생, 기각. ② 자체 API 서버 — 추천 로직이 30~100개 카탈로그의 필터+가중치 계산이라 클라이언트에서 1ms 수준, 서버가 줄 이점 없음, 기각.

## R4. 저장소 — localStorage + 어댑터 계층

- **Decision**: 사용자 상태(취향 프로필·식사 이력·재고·추천 기록·절약 집계)는 localStorage에 버전 태그가 붙은 JSON으로 저장한다. 접근은 `storage/` 어댑터를 통해서만 한다.
- **Rationale**: 데이터 규모가 수십 KB 수준(이력 수백 건·재고 수십 건)이라 localStorage 용량(약 5MB)으로 충분하다. 동기 API라 홈 첫 렌더에서 추천 고정 상태를 즉시 복원할 수 있어 KR1에 유리하다. 어댑터 격리로 IndexedDB 전환 시 도메인·UI 무변경.
- **Alternatives considered**: ① IndexedDB — 비동기라 초기 렌더 경로가 복잡해지고 현 규모에서 이점 없음, 필요 시 어댑터 교체로 대응. ② 파일 내보내기/가져오기 — 백업 요구는 MVP 범위 외, v2 후보로만 기록.

## R5. "하루 고정" 추천의 구현 방식

- **Decision**: 추천 기록 엔티티에 `date`(로컬 자정 기준 날짜)와 현재 추천을 저장하고, 앱 시작 시 오늘 날짜 기록이 있으면 재계산 없이 복원한다. "다른 메뉴 보기"는 기록의 현재 추천을 교체하며 거절 이력을 남긴다. 자정 판정은 기기 로컬 시간 기준.
- **Rationale**: 클래리파이 결정(하루 고정, 자정 경계, 거절 시에만 변경)을 상태 저장으로 직역한 것. 엔진을 결정적(deterministic) 순수 함수로 유지하면서 고정성은 저장 계층이 책임진다 — 테스트가 단순해진다.
- **Alternatives considered**: 날짜 시드 기반 결정적 재계산(저장 없이 같은 날 같은 결과) — 거절로 대체된 추천을 표현할 수 없고, 이력·재고 변화가 당일 중 추천을 바꿔버리는 부작용, 기각.

## R6. 시세·제철·보관기간 데이터 파이프라인

- **Decision**: KAMIS 공공 시세를 수동/스크립트로 월 1회 정리해 `src/data/prices.json`으로 커밋한다(런타임 API 호출 없음). 제철 테이블·재료별 평균 보관 기간도 정적 JSON. 각 파일에 `asOf`(기준 연월) 필드를 두고 화면의 "평균 시세 기준 추정" 문구에 기준 시점을 병기한다.
- **Rationale**: 스펙 FR-019(월 단위 갱신 대략치·추정 명시)를 가장 싼 방식으로 충족. 런타임 외부 의존이 없어 오프라인·장애 엣지 케이스(FR/엣지: 갱신 실패 시 마지막 데이터 + 기준 시점 명시)가 자동으로 해결된다.
- **Alternatives considered**: 런타임 KAMIS API 연동 — CORS·키 관리·장애 대응 비용이 생기고 월 단위 갱신 요구에 과잉, 기각.

## R7. 접점 채널(푸시) — 이번 사이클 제외, 통로만 확보

- **Decision**: 푸시는 구현하지 않는다. PWA 선택으로 웹 푸시 추가 경로만 확보해 둔다.
- **Rationale**: 스펙 가정이 "푸시 없이도 성립하는 앱 내 경험만 요구사항으로 확정"이라고 명시. PRD 오픈 이슈(허용률·발송 시각 전략)는 별도 설계 문서 소관.
- **Alternatives considered**: 로컬 알림 우선 구현 — 전략 미설계 상태에서 발송 시각을 임의 확정하게 되어 PRD의 검증 순서(전략 설계 → 구현)를 역행, 기각.

## R8. 콘텐츠(카탈로그 30개) 접점

- **Decision**: 카탈로그는 `contracts/catalog-schema.md`의 JSON 계약으로 코드와 분리한다. 큐레이션(선별·계량 보정·태깅)은 콘텐츠 작업으로 병행하고, 개발은 계약을 만족하는 샘플 레시피 5개로 진행한다. 로더에서 스키마 검증(15분 비중 50%+, 필수 필드)을 수행해 콘텐츠 오류를 빌드/테스트 단계에서 잡는다.
- **Rationale**: PRD 릴리스 계획(F6a 큐레이션은 검증 스프린트와 병행)과 맞물리며, V4 파일럿 산출물(5개)이 그대로 개발용 샘플이 된다.
- **Alternatives considered**: 코드에 레시피 하드코딩 — 콘텐츠 갱신마다 코드 수정 필요, 큐레이터 역할 분리 불가, 기각.

## R9. 테스트 전략

- **Decision**: TDD로 진행한다. ① `tests/unit/` — 엔진 필터·가중치·완화 순서·자정 경계(fake timer)·절약 계산식·유통기한 추정 등 도메인 순수 함수. ② `tests/integration/` — 스펙의 수용 시나리오(US1~US7)를 스토리지 포함 플로우로 검증. UI 스냅샷 테스트는 하지 않는다(화면이 작고 변동이 잦음).
- **Rationale**: 도메인 코어가 순수 함수라 스펙의 FR 대부분(FR-001~010, 016, 020~022)을 UI 없이 정확히 검증할 수 있다. 수용 판정·하루 고정·지침 모드 해제 같은 시간 의존 로직은 fake timer가 필수.
- **Alternatives considered**: E2E(Playwright) 우선 — 화면 5개 MVP에서 유지 비용 대비 이득 낮음, 수동 스모크로 대체하고 v1.1에서 재평가.
